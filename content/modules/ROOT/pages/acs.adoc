== Feature Overview

Red Hat Advanced Cluster Security (ACS) 5 introduces several new capabilities for securing containerized and virtualized workloads:

. *VM Vulnerability Management* — extends RHACS vulnerability scanning to cover virtual machine workloads running on OpenShift Virtualization. The `roxagent` service runs inside VMs, scans installed packages (RPM/DNF), and reports vulnerabilities to ACS Central via Sensor over VSOCK (pull mode). Organizations gain unified vulnerability visibility across both containers and VMs from a single ACS console.

. *File Activity Monitoring (FAM)* — provides runtime file integrity monitoring. Security teams can define custom file paths (with wildcard support) to monitor for access, modification, and rename operations. File activity criteria can be combined with process-level criteria (process name, ancestor, arguments, UID) in deployment and node policies, enabling detection of unauthorized file access patterns required for compliance frameworks such as PCI-DSS.

. *OpenShift Lightspeed Integration for Risk Enrichment* — uses OpenShift Lightspeed to enrich ACS Risk findings with AI-assisted context: why a deployment ranks high, which signals drive the score, and what remediation to prioritize. Security teams can move from a ranked Risk list to an explained, actionable next step without leaving the console workflow.

. *ACS MCP Server* — exposes ACS Vulnerability Management and Configuration Management APIs as MCP tools, allowing AI agents to interact programmatically with security data.

. *Init Container Security Coverage* — RHACS now evaluates init containers for both image scanning and security policies. When a deployment references init containers, their images are scanned for vulnerabilities using the same process as main container images. Build and Deploy stage policies can be configured to include or exclude init containers using the "Filters" menu.

Each of these features is covered in more detail in the following sections. Part of each walkthrough will be to discuss how the feature is setup, how it works, and how it can be used to secure your environment.

*The ACS team asks that you provide feedback on the feature by completing the structured feedback form at the end of each exercise.*

== Hands-on Exercises

=== Exercise 1: VM Vulnerability Management

In this exercise you will walk through the ACS 5 vulnerability scanning capabilities for OpenShift Virtualization workloads.

==== Understanding the prerequisites for VM vulnerability scanning

Before you verify the prebuilt VM, review what RHACS requires to scan OpenShift Virtualization workloads. These conditions are already met in this lab for `rhel9-vm`.

For full product details, see the link:https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_security_for_kubernetes/4.11/html-single/operating/index#scanning-virtual-machines_examine-images-for-vulnerabilities[Scanning virtual machines^] topic in the RHACS 4.11 Operating guide.

.How RHACS scans virtual machines

RHACS collects, processes, and analyzes VM package data with these components:

`roxagent`::
Quadlet (Podman container managed by systemd) that runs inside the VM. It scans installed packages, caches index reports, and runs in server mode to answer authenticated Sensor requests over VSOCK. In ACS 5.0, this is the supported customer-shipped form of `roxagent`; standalone binaries are used only for local demos and are not shipped to customers.

Sensor::
Cluster-level component that pulls index reports from `roxagent` over VSOCK (via the KubeVirt API), aggregates VM data with Kubernetes API information, and sends it to Central.

Central::
Stores VM information, matches packages against known CVEs (via Scanner V4), and exposes results in the RHACS portal and API.

.Prerequisites

OpenShift Virtualization and RHACS must meet the following requirements in your environment:

NOTE: These requirements are met in this lab.

* The OpenShift Virtualization Operator is installed on the cluster you want to scan.
* The `HyperConverged` resource is patched to enable virtual socket (vsock) support.
* The RHACS feature flag `ROX_VIRTUAL_MACHINES=true` is set on the Central container and the Sensor container.
* Sensor has RBAC permission to use VSOCK (`GET` on the `virtualmachineinstances/vsock` resource).

Each VM to be scanned must meet the following requirements:

* The VM runs Red Hat Enterprise Linux (RHEL) and is registered with Red Hat Subscription Manager with an active RHEL subscription. VM vulnerability scanning does not cover non-RHEL guest operating systems in this release.
* VSOCK is enabled on the VM with `spec.domain.devices.autoattachVSOCK: true`.
* The VM has internet access to download repository-to-Common Platform Enumeration (CPE) mappings.
* DNF is installed.
* `roxagent` runs with privileges sufficient to scan package databases and expose index reports over VSOCK (typically root or sudo).
* At least one DNF transaction (for example, `dnf install`) has been executed on the system to prepopulate required metadata.

=== Exercise 2: File Activity Monitoring (FAM)

In this exercise you will walk through ACS File Activity Monitoring: how it is enabled, which policies this lab already deploys, how to trigger a deployment-scoped violation, and how to confirm it in the Violations UI.

==== Understanding the prerequisites for File Activity Monitoring (FAM)

Before you trigger a violation, review what RHACS requires for file activity monitoring. These conditions are already met in this lab.

For full product details, see the link:https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_security_for_kubernetes/4.11/html-single/operating/index#configuring-file-activity-monitoring_using-policies-to-provide-security[Configuring file activity monitoring^] topic in the RHACS 4.11 Operating guide.

.How RHACS monitors file activity

Collector (per node)::
Observes file operations on monitored paths for containerized workloads and for host processes, then forwards events to Sensor.

Sensor::
Evaluates runtime policies against those events and reports matches to Central.

Central::
Stores violations and exposes them in the portal (deployment events) and API (including node events).

.Prerequisites

RHACS and the secured cluster must meet the following requirements:

* File Activity Monitoring is enabled on the SecuredCluster under `spec.perNode.fileActivityMonitoring.mode: Enabled`.
* Runtime policies use the *File Path* criterion (RHACS 4.11+ field) with either a *Deployment* or *Node* event source.
* The architecture is x86 (currently the only architecture supported for FAM).

NOTE: Node-event violations appear on the Violations page in the RHACS portal, and are also available through notifiers and the `/v1/alerts` API. Machine Config Operator file changes are not detected.

==== Review the preconfigured FAM policies

First, confirm FAM is enabled on the SecuredCluster:

[source,sh,subs="attributes",role=execute]
----
oc get securedcluster -n acs -o jsonpath='{.items[0].metadata.name}{"\n"}{.items[0].spec.perNode.fileActivityMonitoring.mode}{"\n"}'
----

You should see the SecuredCluster name and `Enabled`.

With FAM enabled, this environment deploys two SecurityPolicy resources via GitOps (same pattern as the RHACS demo FAM setup):

* *Deployment File Activity* — `eventSource: DEPLOYMENT_EVENT`, monitors sensitive paths such as `/etc/{asterisk}{asterisk}/{asterisk}`, `/boot/{asterisk}{asterisk}/{asterisk}`, and `/usr/{asterisk}{asterisk}/{asterisk}` for container/workload file activity.
* *Node File Activity* — `eventSource: NODE_EVENT`, monitors the same path patterns for host-level processes (SSH, systemd, and similar).

Review the policies in ACS Central:

. In ACS Central, open *Platform Configuration > Policy Management*.
+
Search for `File Activity` and open *Deployment File Activity*.
+
Confirm:

* *Lifecycle* is *Runtime*
* *Event source* is *Deployment*
* Policy criteria include *File Path* values such as `/etc/{asterisk}{asterisk}/{asterisk}`

. Open *Node File Activity* and confirm the event source is *Node* with the same style of *File Path* criteria.
+
TIP: The GitOps source for these policies is in the lab GitOps repository under `acs/acs-instance/templates/fim-deployment-policy.yaml` and `fim-node-policy.yaml`.

==== Trigger and review a deployment FAM violation

. Trigger a monitored file operation inside an emojivoto pod.
+
OpenShift often runs these containers under a restricted SCC (non-root), so use `oc debug --as-root` against the `web` deployment. That still records as a *deployment* file-activity event for FAM:
+
[source,sh,subs="attributes",role=execute]
----
oc debug -n emojivoto deploy/web --as-root -- touch /etc/passwd
----
+
This matches the *Deployment File Activity* policy (`/etc/{asterisk}{asterisk}/{asterisk}` under a deployment event source).
+
TIP: If `oc debug --as-root` is unavailable in your client, try `oc exec -n emojivoto deploy/web -c web-svc -- touch /etc/passwd`. That succeeds only when the container can write under `/etc`.

. In ACS Central, open *Violations*.
+
Filter by policy name `Deployment File Activity` (or search for `File Activity`).
+
Open a matching violation and review the runtime detail (file path, process context, deployment, and timestamp).

. Optionally confirm the alert count via the ACS API (basic auth):
+
[source,bash,role="execute",subs="+attributes"]
----
CENTRAL="https://central-acs.{openshift_cluster_ingress_domain}"
curl -sk -u "admin:{common_password}" -G "${CENTRAL}/v1/alerts/summary/groups" \
  --data-urlencode 'query=Policy:"Deployment File Activity"' | jq .
----
+
You should see `numAlerts` greater than zero for that policy.

What you just proved:: FAM on the secured cluster observed a container file operation on a monitored path, Sensor evaluated the *Deployment File Activity* runtime policy, and Central recorded a Violations-page alert.

==== Trigger a node FAM violation

Use this path if you want to exercise host-level file activity. Node FAM alerts appear on the Violations page in the RHACS portal, and are also available through the API and notifiers.

. Trigger a host file operation via `nsenter` into PID 1 on a worker node:
+
[source,sh,subs="attributes",role=execute]
----
NODE=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
echo "Using node: ${NODE}"
oc debug "node/${NODE}" --quiet -- bash -c 'nsenter -t 1 -m -u -i -n -p touch /etc/passwd'
----
+
IMPORTANT: Plain `oc debug node` shells are classified as *deployment* events. The `nsenter` into PID 1 is required so RHACS records a *NODE_EVENT*.

. In ACS Central, open *Violations* and filter by policy name `Node File Activity` to confirm the node event. You can also query the alert count via the API:
+
[source,bash,role="execute",subs="+attributes"]
----
CENTRAL="https://central-acs.{openshift_cluster_ingress_domain}"
curl -sk -u "admin:{common_password}" -G "${CENTRAL}/v1/alerts/summary/groups" \
  --data-urlencode 'query=Policy:"Node File Activity"' | jq .
----
+
NOTE: Node FAM alerts now appear on the *Violations* page, and remain available through the API and notifiers.

=== Exercise 4: ACS MCP Server

In this exercise you will walk through the ACS (StackRox) MCP server: how it exposes RHACS APIs as MCP tools, verify the preinstalled endpoint, query security data through OpenShift Lightspeed (and optionally an external MCP client), and capture feedback.

==== Understanding the ACS MCP server

The ACS MCP server is based on https://github.com/stackrox/stackrox-mcp[stackrox-mcp^] (same approach as the RHACS demo `mcp-server-setup`). It exposes RHACS Central data to MCP-compatible clients through toolsets such as:

* *Vulnerability management* — query CVEs, images, deployments, and related findings
* *Configuration management* — read RHACS configuration such as clusters and policies (read-only in this lab)

.How it fits together

ACS MCP server::
Runs in the `acs-mcp` namespace, speaks streamable HTTP MCP on `/mcp`, and calls Central on behalf of the client.

Authentication::
External clients use *passthrough* auth: your MCP client sends `Authorization: Bearer <ACS API token>`. OpenShift Lightspeed is pre-wired with an Analyst token via secret `acs-mcp-api-token`.

AI client::
OpenShift Lightspeed (in-console) or an external MCP client (Claude Code, Cursor, Claude Desktop) discovers tools and answers natural-language security questions.

.Prerequisites

* The ACS MCP server Deployment and Route are available in `acs-mcp` (preinstalled via GitOps).
* Central is reachable and the secured cluster is reporting data (completed in *Before You Begin*).
* For Lightspeed: OLSConfig includes the `MCPServer` feature gate and an `acs-mcp` server entry (already configured in this lab).
* For an external client: an ACS API token with at least the *Analyst* role.

=== Exercise 5: Init Container Security Coverage

In this exercise you use the init-container workload deployed in *Before You Begin*, confirm ACS sees the containers and scans the init image, create a Build/Deploy policy that can match or skip init containers, edit the policy Filters, then review the resulting violations in ACS.

The workload is `nginx-with-waitfor` in namespace `acs-init-demo`: init container `wait-for-api` (`ghcr.io/kitstream/initium:latest`) plus an unprivileged `nginx` main container.

==== 1. Sanity test: inspect containers in ACS

. Confirm the pre-deployed init-container example is running:
+
[source,sh,subs="attributes",role=execute]
----
oc get deploy,pods -n acs-init-demo
oc get deploy nginx-with-waitfor -n acs-init-demo -o jsonpath='{range .spec.template.spec.initContainers[*]}{.name}{" -> "}{.image}{"\n"}{end}{range .spec.template.spec.containers[*]}{.name}{" -> "}{.image}{"\n"}{end}'
----
+
You should see init container `wait-for-api` and main container `nginx`. If the namespace is missing, re-apply from *Before You Begin*:
+
[source,sh,subs="attributes",role=execute]
----
oc apply -f - <<'EOF'
include::example$init-container-demo.yaml[]
EOF
----

. In ACS Central, open *Configuration Management > Deployments*.
. Find `nginx-with-waitfor` in namespace `acs-init-demo`.
. Open the deployment and confirm both containers appear: init `wait-for-api` and main `nginx`.
. Apply the container-type filter *Container Type: INIT* (wording may vary slightly by build). Confirm `wait-for-api` remains listed and is typed as an init container.

==== 2. Image scanning in Vulnerability Management

. In ACS Central, open *Vulnerability Management > Results* (Images or Deployments view).
. Locate the init image `ghcr.io/kitstream/initium:latest` (or the digest ACS resolved for it).
. Confirm the image has a scan result and that findings are attributable to the init container / that image — not only to the main `nginx` image.
. Open *Risk*, select `nginx-with-waitfor`, and check whether image vulnerabilities for the init container appear in the risk indicators.

==== 3. Policy behavior: create a Build/Deploy policy

The init image uses the mutable tag `latest`. Create a Build and Deploy policy that matches that tag, with *Filters* left at the default so all container types (including init) are evaluated.

. In ACS Central, open *Platform Configuration > Policy Management* → *Create policy*.
. Configure the policy as follows:
+
* *Name*: `EA Init Container - Latest Tag`
* *Lifecycle*: enable *Build* and *Deploy*
* *Severity*: Medium or High
* *Policy criteria*: *Image Tag* → `latest`
* *Filters*: leave at the default (all container types, including init)
* *Enforcement*: *Inform* / notify (do not block)

. Save and enable the policy.

==== 4. Edit Filters to match or skip init containers

. Edit `EA Init Container - Latest Tag`.
. Set *Filters* to *skip init containers* (exact label may read "Exclude init containers" or similar).
. Save the policy and allow about a minute for re-evaluation.
. Confirm the init-container `:latest` match for `wait-for-api` stops firing while the policy remains enabled.
. Edit the policy again and set *Filters* back to the default so init containers are included.
. Save and allow about a minute for re-evaluation so init-container matches return.

==== 5. Review violations in ACS

. Open *Violations* in ACS Central.
. Filter or search for policy `EA Init Container - Latest Tag` and deployment `nginx-with-waitfor`.
. Confirm a violation is present that references the init image tag `latest` and, where shown, init container `wait-for-api`.
. Open the violation details and note whether attribution to the init container (name/image) is clear enough to act on.
. Compare with *Configuration Management* and *Vulnerability Management* for the same deployment: the containers, scan findings, and policy violation should tell one coherent story for this init-container workload.
+
NOTE: If the violation attributes only to the deployment without naming the init container, capture that in the feedback form — attribution UX is part of what this EA exercise validates.
